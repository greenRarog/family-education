# A12 — подтверждение прочтения

Дата: 27 октября 2026 года. **A12 выполнен, PASS после исправления A12.1: 16 тестовых случаев, 163 утверждения.** Проверены `POST /api/conversations/{id}/read`, состояние сообщений, unread и курсор прочтения у отправителя.

## A12.1 — согласованность ответа

Четыре исходных теста прошли (14 утверждений), но не покрывали границы подтверждённого курсора и точность времени. Новый [ReadReceiptTest](../tests/Feature/ReadReceiptTest.php) до исправления дал 6 PASS / 6 FAIL из 12 случаев:

- Входной through_id возвращался без нормализации. При максимальном id=4 сервер мог подтвердить 1004; чужой id в промежутке возвращался вместо последней существующей границы текущего диалога. Даже для пустого диалога возвращался присланный id.
- Числовая строка возвращалась строкой, а не числом.
- Ответ read_at содержал микросекунды, тогда как Eloquent сохранял время с секундной точностью: например, `.123456Z` в ответе против `.000000Z` в БД.

В [MessageController::read](../app/Http/Controllers/v1/Api/MessageController.php) изменено только вычисление границы и времени. Сервер выбирает максимальный существующий id текущего диалога, не превышающий запрошенный, и возвращает int/null. При отсутствии границы сохраняется прежний режим — максимум текущего диалога. `now()->startOfSecond()` согласует read_at ответа с точностью сохранения.

Условия UPDATE сохранены: только текущий диалог, id не выше подтверждённой границы, автор не равен текущему пользователю, read_at ещё null. Доступ и правила валидации не менялись.

## Контракт после исправления

| Вход / состояние | Результат |
| --- | --- |
| Существующий through_id | Подтверждается этот id; отмечаются только входящие непрочитанные сообщения до него включительно. |
| Чужой или отсутствующий id между сообщениями | Подтверждается ближайший меньший существующий id текущего диалога. Чужие сообщения не затрагиваются. |
| Завышенный through_id | Подтверждается максимум текущего диалога. Ответ не подтверждает ещё не существующие сообщения. |
| through_id меньше первого id / пустой диалог | through_id=null, сообщений для обновления нет. |
| Числовая строка | После проверки возвращается целое число. |
| Поле отсутствует, null или пустая строка | Используется максимум текущего диалога; прежний режим «отметить доступные сейчас сообщения» сохранён. |
| 0, отрицательное, дробное, нечисловое значение или массив | 422 с ошибкой through_id, сообщения не меняются. |
| Гость / посторонний | 401 / 403, сообщения не меняются. |

Граница receipt может указывать на **своё** сообщение: это позволяет клиенту подтвердить всю полученную страницу и не повторять один запрос бесконечно. Собственное сообщение при этом не помечается прочитанным. `read_by_other_through_id` в detail у отправителя имеет другой смысл: максимальный id **его сообщений**, реально прочитанных другой стороной. Поэтому эти два курсора не обязаны совпадать; тест обеих ролей проверяет соответствующие значения.

`read_at` ответа — время обработки текущего подтверждения с секундной точностью. Для сообщений, впервые отмеченных этим запросом, оно совпадает с БД. Повтор не перезаписывает прежние даты, но возвращает время нового подтверждения. Идемпотентность здесь относится к состоянию сообщений, а не к побайтовой одинаковости ответов. Запрос более старой границы не отменяет ранее сохранённые отметки; ответ содержит эффективную границу именно текущего запроса, не глобальный монотонный курсор.

## Проверенное поведение

- Для владельца объявления и автора отклика: входящее сообщение до границы отмечается, своё и входящее после неё остаются непрочитанными; чужой диалог не меняется.
- Ранее прочитанные сообщения сохраняют исходные даты. Повтор через пять минут и запрос более старой границы не перезаписывают их.
- Расширение границы отмечает следующее входящее сообщение; unread в списке и общем счётчике меняется с 1 на 0, курсор отправителя продвигается до правильного входящего id.
- После добавления нового сообщения повтор с подтверждённой границей оставляет его непрочитанным, в том числе после исходного завышенного запроса.
- Проверены пустой диалог, диалог только со своими сообщениями, omitted/null/empty через отдельные случаи, границы до первого/между/после последнего id, числовая строка и точность времени.
- Существующие четыре теста read receipt и изоляции тоже прошли.

Чтение frontend-кода подтверждает, что он использует receipt.through_id как подтверждённую границу и применяет read_at только к входящим сообщениям без даты. Frontend не менялся и браузерный прогон здесь не выполнялся.
