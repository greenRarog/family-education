# A11 — порционная история сообщений

Дата: 27 октября 2026 года. **A11 выполнен, PASS после исправления A11.1: 8 тестовых случаев, 325 утверждений.** Найден и устранён дефект валидации, вызывавший HTTP 500 при запросе истории с курсором.

## A11.1 — исправление HTTP 500

Исходный запуск двух существующих тестов истории завершился FAIL: 2 теста, 9 утверждений. Запрос `GET /api/conversations/{id}/messages?before_id=...` для участника диалога падал с исключением:

```text
BadMethodCallException:
Method Illuminate\Validation\Validator::validateProhibitedWith does not exist.
```

В [ConversationController::messages](../app/Http/Controllers/v1/Api/ConversationController.php) оба курсора использовали несуществующее правило `prohibited_with`. Оно заменено на поддерживаемое `prohibits`:

```php
'before_id' => ['nullable', 'integer', 'min:1', 'prohibits:after_id'],
'after_id' => ['nullable', 'integer', 'min:0', 'prohibits:before_id'],
```

Поведение `prohibits` проверено по исходнику установленного Laravel (`ValidatesAttributes::validateProhibits`) и API-тестами. Один непустой курсор разрешён; два непустых, включая `after_id=0`, дают 422 с ошибками обоих полей. Пустой nullable-курсор не конфликтует с заполненным.

Сразу после замены исходные два теста прошли: 2 теста, 25 утверждений. Это единственное изменение приложения в A11 — две строки правил; запросы, размер порции, сериализация и авторизация не менялись.

## Проверенный контракт

| Endpoint | Результат |
| --- | --- |
| `GET /api/conversations/{id}` | Последние максимум 50 сообщений в порядке id по возрастанию; has_older показывает наличие более старых сообщений, has_more=false. |
| `GET /api/conversations/{id}?after_id=N` | Первые максимум 50 сообщений с id>N, по возрастанию; has_more показывает продолжение вперёд, has_older=false. |
| `GET /api/conversations/{id}/messages` | Последние максимум 50, по возрастанию; meta.has_more означает наличие более старой истории. |
| `GET /api/conversations/{id}/messages?before_id=N` | Последние максимум 50 сообщений с id<N, по возрастанию; meta.has_more означает продолжение назад. |
| `GET /api/conversations/{id}/messages?after_id=N` | Первые максимум 50 сообщений с id>N, по возрастанию; meta.has_more означает продолжение вперёд. |

Курсоры исключают саму граничную запись. oldest_id/latest_id в detail обозначают первое/последнее сообщение возвращённой порции, а не глобальные границы диалога. Для пустой порции оба равны null. after_id=0 начинает чтение с начала; before_id должен быть не меньше 1. При отсутствии/пустых курсорах выполняется начальный запрос. Передавать before_id нужно в endpoint `/messages`; detail использует только after_id.

## Что подтверждено тестами

В [ConversationPaginationTest](../tests/Feature/ConversationPaginationTest.php) расширены два теста истории, добавлены параметризованные границы и проверка разрывов ID:

- **0/1/49/50/51 сообщений:** размеры и содержимое порций обоих endpoint, корректные флаги продолжения, oldest_id/latest_id, after_id=0, пустые курсоры и достижение конца истории. При ровно 50 has_more=false; при 51 — true для первой соответствующей порции.
- **120 сообщений и новые поступления:** начальные последние 50, затем добавление ещё трёх. Старые страницы before_id продолжают возвращать исходные сообщения без сдвига. Объединение старых порций и начальной страницы точно совпадает с исходными 120 id.
- **Проход вперёд:** оба endpoint с after_id возвращают идентичные сообщения порциями 50/50/23; объединение точно совпадает со всеми 123 id без пропусков и дублей. Пустой запрос после последнего сообщения завершает проход. Время заморожено: порядок устойчив и при одинаковом created_at.
- **Разрывы ID:** сообщения другого диалога вставлены между сообщениями текущего. Курсор может быть числовым порогом из чужого диалога, но выборка всё равно содержит только сообщения текущего; существование/принадлежность записи курсора не является условием контракта.
- **Авторизация:** гость получает 401, посторонний — 403 без messages/conversation для начальных и курсорных запросов. Владелец объявления и автор отклика получают ожидаемое сообщение через оба endpoint.
- **Ошибки:** отрицательные, дробные, нечисловые и массивные курсоры дают 422 с ошибкой поля; before_id=0 отклоняется. Конфликт before_id/after_id даёт 422, включая after_id=0.

Read receipts и их метаданные относятся к A12 и здесь не проверялись. Тесты списка A10 и сценарии A12/A13 в том же файле сохранены без изменений.
