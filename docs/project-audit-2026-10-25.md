# Исследование проекта и план реализации

Дата: 25 октября 2026 года.

Исследованы три локальных репозитория: backend (`e5e1e58`), frontend (`eeb38f3`), infrastructure (`932d4eb`). Основание — README, маршруты, модели, миграции, контроллеры, страницы React, тесты и конфигурация запуска/CI. Рабочий код не изменялся.

## Вывод

Проект уже содержит основной функциональный срез доски объявлений для семейного образования. Следующая задача — довести существующие сценарии до надёжного состояния и реализовать минимальную модерацию. Начинать педагогический модуль заново не нужно: он уже существует, хотя README относит его к будущим этапам.

Готовность production не подтверждена: обнаружены дефекты приватности и пользовательских сценариев, отсутствует часть административных функций, функциональные проверки в этой среде недоступны.

## Подтверждённые чтением кода дефекты

### A01. Публичная выдача полных данных детей — P0

`backend/app/Http/Controllers/v1/Api/AdvertisementController.php:33,137,260` возвращает Eloquent-модели объявлений с отношением `children` в публичных feed/show. `backend/app/Models/Child.php` не ограничивает сериализацию: доступны имя, дата рождения, пол, `family_id`, идентификаторы и служебные поля. Отсутствие этих полей на экране не ограничивает доступ через JSON.

Исправление: отдельный публичный API Resource с разрешённым списком полей. Для поиска использовать возрастной диапазон объявления; данные детей возвращать только владельцу в приватном API. Проверить карточки и формы frontend на зависимость от прежнего ответа.

Приёмка: тесты гостя и постороннего пользователя подтверждают отсутствие идентифицирующих данных детей в feed/show; владелец по-прежнему может редактировать выбранных детей.

### A02. Backend CI остался от монорепозитория — P0 для процесса разработки

`backend/.github/workflows/ci.yml:43–56` выполняет Node setup с npm cache, `npm ci` и `npm run build`, хотя в backend больше нет `package.json` и npm lockfile. Чистый checkout не соответствует workflow. README ошибочно считает разделение проверок завершённым.

Исправление: убрать сборку frontend из backend CI, оставить Composer/style/static analysis/tests. Проверить реальный драйвер тестовой БД: `phpunit.xml` задаёт SQLite, workflow передаёт PostgreSQL. Явно организовать хотя бы один прогон миграций и интеграционных тестов на PostgreSQL.

Приёмка: независимые backend/frontend CI проходят на чистых checkout; infrastructure получает проверку Compose и сборки без запуска stage.

### A03. Кнопка отзыва принятого отклика не работает — P1

В `frontend/src/pages/ConversationShow.jsx:166` обработчик разрешает действие только при статусе `sent`. Кнопка «Отозвать отклик» при `accepted` вызывает тот же обработчик (`:310`) и немедленно получает `return`. Backend переход `accepted → rejected` поддерживает.

Исправление: проверять допустимые переходы по запрашиваемому действию; согласовать UI и API.

Приёмка: браузерный сценарий принятия и последующего отзыва проходит; дальнейшая отправка сообщений запрещена обоим участникам; история остаётся доступна.

### A04. Письмо об истечении объявления ссылается на отсутствующий шаблон — P1

`backend/app/Notifications/AdvertisementExpiredNotification.php:41` использует `emails.notifications.advertisement-expired`, но файл называется `backend/resources/views/emails/notifications/dvertisement-expired.blade.php`.

Текущий `AdvertisementExpiredNotificationTest` проверяет строковое имя view, не рендерит письмо, поэтому такой дефект не обнаруживает.

Исправление: согласовать имя файла и view; добавить проверку реального рендеринга всех типов писем для RU/EN/ES.

Приёмка: письмо рендерится и обрабатывается queue worker в тестовом окружении.

### A05. Переписка не обновляется во время просмотра — P1

`ConversationShow.jsx` загружает диалог при открытии/смене ID; периодического запроса или подписки на события нет. Собственные сообщения добавляются локально, сообщения собеседника и изменение статуса отклика автоматически не приходят. `frontend/src/layouts/Layout.jsx` получает счётчик непрочитанных только при монтировании.

Исправление: для MVP достаточно периодического обновления при активной вкладке, обновления после действий и общего состояния счётчика. Не отмечать сообщения прочитанными локально, если запрос `/read` завершился ошибкой.

Приёмка: два пользователя видят новые сообщения и изменение статуса без перезагрузки; счётчик уменьшается после успешного чтения, ошибки запроса не маскируются.

### A06. Недоступны диалоги после первой страницы — P1

`ConversationController.php:44` ограничивает выдачу 20 диалогами. `frontend/src/pages/Conversations.jsx:14` всегда запрашивает URL без `page` и не содержит управления страницами. Контракт ответа также нужно привести к явным `data/links/meta`: коллекция ресурсов сейчас вложена в произвольный JSON.

Дополнительно список диалогов загружает всю историю каждого диалога через `messages.user`; открытие диалога тоже получает все сообщения без ограничения.

Исправление: метаданные и управление страницами списка; последнее сообщение и unread count в списке; отдельная порционная загрузка истории с устойчивым порядком.

Приёмка: доступны 21-й и последующие диалоги; большой чат не загружается целиком при открытии списка.

### A07. Фильтр возраста исключает услуги без возрастных ограничений — P1

Возраст для услуг педагога может быть `null`, но `AdvertisementController::feed()` применяет только `participant_age_from <= age` и `participant_age_to >= age`. Такие услуги не проходят фильтр по конкретному возрасту.

Исправление: определить смысл отсутствующего диапазона. Если это «любой возраст», включать такие объявления через условия `IS NULL`.

Приёмка: тесты услуг без диапазона и с диапазоном, включая обе границы; понятная подпись в UI.

## Дополнительные технические задачи

- Конкурентные отклики: уникальный индекс уже предотвращает дубликаты, но предварительный `exists()` не устраняет гонку двух запросов. Обработать конфликт уникальности предсказуемым ответом вместо возможного 500; проверить на PostgreSQL.
- Выдача услуг педагогов: `appendPublicTeacher()` выполняет дополнительные запросы для каждого объявления. Загружать необходимые связи пакетно и контролировать число запросов.
- Истечение объявлений: ежедневная команда закрывает записи, но не заполняет `closed_at`, в отличие от ручного закрытия. Определить допустимую задержку истечения и единые инварианты перехода статуса.
- Валидация детей: при редактировании проверяется формат даты рождения, но нет запрета даты в будущем. Добавить согласованные ограничения на регистрацию и редактирование.
- Подтвердить матрицу ролей при отклике: для `teacher_to_service` доступ ограничен семьёй; остальные направления не ограничены по типу откликающегося. Это требует продуктового решения, а не автоматического объявления ошибкой.
- Вынести повторяющиеся проверки доступа и переходы статусов в policies/небольшие сервисы по мере исправлений. Полная перестройка монолита для этого не нужна.
- Проверить локализацию серверных ошибок, пустые состояния, 401/403/404/419 и поведение форм при сетевых сбоях; добавить явные guards приватных/admin страниц. Backend уже проверяет доступ, отсутствие frontend guard само по себе не является обходом авторизации.
- Убрать устаревшие пустые/дублирующие frontend-модули после проверки импортов; это низкий приоритет.

## План реализации

Оценки — предварительные трудозатраты одного разработчика, знакомого с проектом, в рабочих днях. Это не календарные обязательства: они не включают ожидание продуктовых решений, доступа к VPS и внешним сервисам. Порядок важнее точных сроков.

| Этап | Работы | Оценка | Критерий завершения |
| --- | --- | --- | --- |
| 0. Воспроизводимость | Исправить backend CI; подготовить доступное тестовое окружение; прогнать текущие тесты и сборки; обновить README по факту Teacher/CI | 1–2 дня | Проверки воспроизводятся на чистом checkout; известны реальные ошибки тестов |

Дополнительные возможности | Telegram bind/unbind и пробная доставка; настройки уведомлений для обеих ролей; затем диплом/SEO по подтверждённым требованиям | Telegram и настройки: 2–4 дня; остальное отдельно | Пользователь сам подключает канал и получает тестовое уведомление; новые возможности имеют сквозную проверку |

Этапы 0–5: ориентировочно 19–32 рабочих дня. Уточнить после этапа 0, когда будут доступны результаты функциональных тестов. A01 нужно исправлять в самом начале, одновременно с восстановлением CI, а не откладывать до завершения прочих подготовительных работ. E2E добавлять вместе с исправляемыми сценариями; не переносить все тесты в отдельный финальный этап.

Рекомендуемое разбиение первых PR:

1. `fix: restrict public advertisement data` — публичный Resource и проверки приватности.
2. `ci: run backend checks independently` — самостоятельный backend CI и явная конфигурация тестовой БД.
3. `fix: render advertisement expiration email` — имя шаблона и тесты рендеринга.
4. `fix: allow terminating accepted conversations` — переход статуса и браузерный тест.
5. `feat: paginate and refresh conversations` — контракт пагинации, ограниченная история, обновление и unread.
6. `fix: include unrestricted teacher services in age filter` — согласованная семантика возраста и проверки.
7. `feat: limit public write actions` — лимиты и предсказуемая обработка конфликтов.

## Решения, необходимые перед соответствующими этапами

Эти вопросы не мешают начинать исправления существующих дефектов.

- Какие данные детей допустимы публично? Рекомендуемый минимум — возрастной диапазон без имён и точных дат рождения.
- Какие роли могут откликаться на каждый тип объявления? Когда требуется подтверждённый email?
- Кто может жаловаться, какие причины допустимы, что означает блокировка и возможна ли апелляция?
- Что происходит с сообщениями второго участника при удалении аккаунта? Каковы сроки хранения и состав анонимизируемых данных?
- Нужны ли дипломы в MVP, кто имеет право их видеть и проверять? Текстовое образование уже реализовано.
- Являются ли Telegram, MAX и индексация поисковиками условиями запуска или следующими этапами?

- Браузерные сценарии, PostgreSQL/Redis runtime, реальная отправка писем/Telegram, состояние VPS, backup restore и deployment не проверялись.

Установка зависимостей, запуск или изменение stage, миграции и изменения рабочих данных в ходе исследования не выполнялись. Единственное изменение — этот документ.
