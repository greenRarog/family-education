# Роли и лимиты действий

29 октября 2026. Утверждённые правила этапа B реализованы в API/UI.
Это действующая спецификация; [краткий итог и приёмка](refactoring-plan-2026-10-26.md#b-защита-действий-и-небольшой-рефакторинг--реализован).

## Объявления и отклики

| Тип объявления | Кто создаёт | Кто может оставить новый отклик |
| --- | --- | --- |
| `family_to_family` — учебная группа | Семья с семейным профилем | Только другая семья |
| `family_to_teacher` — поиск педагога | Семья с семейным профилем | Только педагог |
| `teacher_to_service` — занятия | Педагог с профилем | Только семья |

Гость может читать опубликованные объявления, но не создавать их и не
откликаться. Администратор не получает права создавать объявления или обходить
ограничения. Публикация публичного профиля педагога не является условием
публикации его объявления; это правило сохраняется.

Общие правила сохраняются: нельзя откликнуться на своё или неопубликованное
объявление; один пользователь оставляет не более одного отклика на объявление,
включая уже отклонённый. Первый текст обязателен, не длиннее 5000 символов.
Ошибки: гость — 401, неподходящая роль — 403, своё/неопубликованное/повтор — 422.
При валидном теле: auth, запрет собственного объявления, роль, статус, повтор.
Невалидное тело FormRequest отклоняет до проверок контроллера.

Редактировать, публиковать и закрывать объявление может только владелец;
публикуется только draft, закрытое не редактируется. Принять отклик (sent →
accepted) или завершить его (sent/accepted → rejected) может только владелец
объявления. Первое сообщение создаётся вместе с откликом; до accepted новые
сообщения может отправлять только владелец объявления, после — оба участника,
после rejected — никто. История доступна участникам; посторонним и
администратору без участия доступ не предоставляется.

Матрица применяется только к новым откликам. Существующие отклики, сообщения
и статусы участников их диалогов сохраняются; блокировка дополнительно ограничивает действия по C05. API возвращает `viewer.can_respond`;
frontend показывает форму только при разрешении сервера, сохраняет действия
владельца и отметку прежнего отклика. Backend и frontend передавать согласованно:
при отсутствии нового поля интерфейс не разрешает отправку.

## Согласованные лимиты запросов

Создание, публикация, новые отклики и сообщения используют независимые named limiter.
Ограничение входа Fortify существует отдельно и здесь не меняется.
Числа ниже утверждены для MVP; они не основаны на измерении нагрузки.

| Действие | Запросы за 60 секунд | Дополнительное окно | Ключи счётчиков |
| --- | ---: | --- | --- |
| Создать черновик: POST `/api/advertisements` | 5 | 20 за 86400 секунд | `ads:create:user:{id}:{window}` |
| Опубликовать: POST `/api/advertisements/{id}/publish` | 5 | 20 за 86400 секунд | `ads:publish:user:{id}:{window}` |
| Откликнуться: POST `/api/advertisements/{id}/responses` | 5 | 50 за 86400 секунд | `responses:create:user:{id}:{window}` |
| Отправить сообщение: POST `/api/conversations/{id}/messages` | 30 | 300 за 3600 секунд | `messages:create:user:{id}:{window}` |

- `{id}` в ключе — ID авторизованного пользователя; `{window}` — длительность
  окна в секундах. Счётчики разные для действий и окон, общие для всех типов
  объявлений/диалогов пользователя. IP не входит в ключ; смена сессии не сбрасывает лимит.
- Оба окна действуют одновременно; каждое длится указанный срок от первого
  учтённого запроса. Это не календарный день и не скользящее окно.
- Считаются попытки, дошедшие до limiter после session/CSRF/auth, включая
  дальнейшие 403/422. Отказы до limiter не учитываются; 429 не продлевает окно.
  При исчерпанном лимите 429 может предшествовать проверкам контроллера.
- При превышении — JSON 429 с понятным сообщением и `Retry-After` в секундах,
  достаточным для освобождения всех блокирующих окон; без записей и событий.
  Счётчики должны разделяться процессами приложения через общий cache store.
- Создание и публикация имеют независимые бюджеты. Первый текст отклика
  учитывается только в лимите откликов; чтение, polling и read receipts не
  расходуют лимит сообщений. Ограничений на общее число сохранённых/активных
  объявлений нет; правила подтверждения email описаны ниже.

## Обработка отказов и конкурентного отклика

- JSON 429 содержит `retry_after` и заголовок `Retry-After` с максимальным ожиданием.
  Frontend показывает срок на RU/EN/ES; без срока — общее сообщение. Ввод сохраняется,
  повтор ручной; повтор публикации услуги использует уже созданный черновик.
- Для рабочих процессов нужен общий cache store (например, database), не array/null.
- Уникальный индекс пары и `createOrFirst` с savepoint внутри транзакции обрабатывают
  конкурентный дубль: 201 и JSON 422 «Вы уже откликались на это объявление.».
  Создаются один отклик, диалог, первый текст, событие и уведомление;
  другие ошибки БД не маскируются под дубль.

## Подтверждение email

Политика утверждена пользователем и реализована. Действует для старых и новых аккаунтов.

### Утверждённая матрица действий

Все прежние роли, владение, статусы и численные лимиты сохраняются.
Подтверждение email не даёт дополнительных прав роли.

| Действие | Требовать подтверждённый email |
| --- | --- |
| Вход/выход, регистрация, просмотр публичных объявлений/профилей/справочников | Нет |
| Свой кабинет, язык, настройки уведомлений, профиль семьи/детей | Нет |
| Создание и изменение своего черновика объявления | Нет; остаётся лимит создания |
| Публикация объявления; изменение уже опубликованного объявления | Да |
| Закрытие своего объявления | Нет |
| Новый отклик с первым сообщением на любой тип объявления | Да, для автора отклика |
| Список/история своих диалогов, polling, непрочитанные, read receipts | Нет |
| Принятие/отклонение существующего отклика, сообщения в созданном диалоге | Нет; прежние права участников и статусы сохраняются |
| Сохранение профиля педагога с `public_profile_requested=false`, снятие с публикации | Нет |
| Сохранение профиля педагога с `public_profile_requested=true` | Да; включает запрос публичности и правки публичного профиля |
| Admin GET в рамках роли | Нет |
| Admin POST/PUT/PATCH/DELETE | Да; одобрение публичного профиля также требует подтверждения его владельца |
| Подтверждение, повторное письмо, восстановление пароля | Нет |

- Причина выбора: проверять адрес перед новой публичной активностью/контактом,
  оставляя подготовку данных и продолжение переписки. Правки опубликованного
  объявления и публичность педагога не должны обходить проверку публикации.
- Осознанный компромисс: неподтверждённый участник может писать в существующем
  диалоге по прежним правилам. Ограничение всех сообщений оборвёт старые контакты;
  лимит сообщений продолжает действовать, verification не заменяет защиту от спама.

### Старые аккаунты, объявления и диалоги

- Единое правило для старых и новых аккаунтов: существующий non-null
  `email_verified_at` сохраняется; null требует подтверждения для закрытых действий.
  Не проставлять дату массово и не выдавать исключение по возрасту аккаунта.
- Аккаунты/сессии, публикации, одобренные профили, отклики и сообщения не удалять
  и не скрывать автоматически. Новые отклики на прежнее объявление разрешать
  подтверждённым авторам независимо от email владельца объявления.
- Переписку сохранять без даты отсечения: правила таблицы действуют и для
  диалогов, созданных после включения политики. До accepted пишет владелец
  объявления; после accepted — оба; после rejected — никто. Чужой доступ закрыт.
- Старое pending-одобрение профиля ждёт подтверждения владельца; текущую
  approved-публикацию не отзывать. Новые сохранения публичного профиля — по таблице.
- Обычные email-уведомления о сообщениях/откликах/истечении отправлять только на
  подтверждённый адрес и при включённой настройке; старые письма не досылать.
  Для очереди проверять условие также перед доставкой. История в кабинете и
  Telegram остаются по прежним правилам. Verification/reset — служебные письма,
  не зависят от пользовательского выключателя уведомлений.

### Письма и восстановление — утверждённый сценарий

- После регистрации отправить первое письмо, оставить пользователя в сессии.
  Для старых аккаунтов — заметное приглашение подтвердить адрес; без массовой
  автоматической рассылки и без отправки на каждом входе/заблокированном действии.
- Повтор: только текущему авторизованному пользователю на сохранённый email,
  без произвольного адреса в запросе; вручную, не чаще 1 раза за 60 секунд и
  5 раз за 3600 секунд на ID, общий cache. Первое письмо входит в этот бюджет.
  429 с Retry-After/retry_after; отказ не отправляет письмо и не продлевает окно.
  Уже подтверждённому — успешный ответ без нового письма.
- Подписанная ссылка — 60 минут, текущий ID/email, вход в тот же аккаунт обязателен.
  На другом устройстве — вход и возврат к ссылке; чужая сессия её не подтверждает.
  Старые ссылки остаются действующими до своего срока; повторная отправка их
  не отзывает. Повтор валидной ссылки после успеха — без повторных изменений/событий.
  Просроченная/изменённая ссылка — понятная ошибка и ручной запрос новой.
  Проверку ссылок оставить отдельно ограниченной 6 запросами в минуту.
- При недоставке — проверить адрес/спам, повторить после ожидания; не обещать
  доставку по ответу API. Ошибка почтового канала не должна удалять аккаунт
  или лишать входа; ограничения публикации/нового отклика остаются до подтверждения.
- Восстановление пароля доступно без verification (из гостевого состояния;
  вошедший пользователь сначала выходит). Сохранить срок токена и интервал
  broker 60 минут/60 секунд; успешный reset не подтверждает email автоматически.
  Затем вход и отдельное verification-письмо; существующую подтверждённость не сбрасывать.
- При ошибке в адресе/потере ящика автоматического восстановления без него нет:
  сначала восстановить почтовый ящик у провайдера. Смена email/ручное восстановление
  требуют отдельного согласованного процесса проверки владельца; не включать
  отключённый updateProfileInformation и не предлагать обход проверки.
  Если смена email будет реализована отдельно — сбрасывать подтверждение,
  инвалидировать ссылки старого адреса, сохранять аккаунт/историю.

### Порядок проверок и выпуск

Auth/CSRF и limiter предшествуют проверке email: её 403 расходует бюджет,
исчерпанный бюджет даёт 429; отказ не создаёт бизнес-записей/событий.
Выпускать backend/frontend согласованно, сохраняя публичный путь ссылки
через `/auth/` и относительную подпись.

### Контракт backend

- `/api/user`: `user.email_verified` (bool), `user.email_verified_at` (ISO/null).
  Ограниченные действия возвращают JSON 403 `code=email_verification_required`;
  одобрение неподтверждённого педагога — `profile_email_verification_required`.
- Маршруты verification теперь принадлежат приложению в routes/web.php;
  одноимённые Fortify-маршруты отключены, регистрация/вход остаются Fortify.
  GET `/email/verify/{id}/{hash}`: auth + signed:relative + 6/мин на ID;
  POST `/email/verification-notification`: auth/CSRF + общий сервис первого/повторного письма.
- Письмо ведёт на frontend `/verify-email/{id}/{hash}?expires=…&signature=…`.
  Frontend сохраняет query и после входа вызывает GET
  `/auth/email/verify/{id}/{hash}` с тем же query, credentials и JSON Accept.
  Nginx снимает `/auth`; подписан именно внутренний путь, не внешний host/scheme.
  Основа ссылки — публичный APP_URL. Экран ожидания — `/verify-email`.
- Проверка ссылки: 200 `email_verified=true`, повтор без повторного Verified;
  гость — 401; плохая/истёкшая подпись — 403 `verification_link_invalid`;
  чужой ID/hash — 403. Статус интерфейса брать из API, не из параметров ссылки.
- Повтор: 202 `status=verification_link_sent`, подтверждённому — 204;
  429 с Retry-After/retry_after; сбой отправки — 503 `verification_delivery_failed`.
  Первая отправка при регистрации использует тот же бюджет; её сбой не мешает
  созданию сессии. Ошибка отправки расходует попытку; успешный API не гарантирует доставку.
- Счётчики `email:verification:user:{id}:60/3600` и атомарный lock используют
  общий cache store (`cache.limiter`, иначе `cache.default`); database подходит.
  Отказ по бюджету не продлевает окно. При занятом lock после ожидания — 429/1с.
- Сохраняются роли/лимиты, старые данные и диалоги. Mail-канал трёх обычных
  уведомлений проверяет подтверждение/настройку при постановке и перед доставкой;
  C05 дополнительно проверяет блокировки для mail/Telegram. Миграций и массового подтверждения нет.
### Восстановление пароля

- Стандартное письмо ведёт на `APP_URL/reset-password/{token}?email=…`;
  token/email URL-кодированы, адрес сайта не берётся из запроса. Fortify views
  остаются отключены; используется существующий frontend-экран.
- POST `/auth/forgot-password` и `/auth/reset-password` остаются прежними.
  Broker: повтор через 60 секунд (раньше — прежний 422), токен 60 минут;
  новое письмо заменяет старый токен, успешный reset расходует токен.
- Служебное письмо доступно неподтверждённому пользователю и при выключенных
  обычных уведомлениях. Reset не меняет email-статус и не создаёт сессию автоматически.
### Интерфейс подтверждения

- Экран ожидания после регистрации, ручной resend/cooldown, подписанная
  ссылка, вход в нужный аккаунт с безопасным возвратом, RU/EN/ES. API определяет
  статус; некорректный ответ, чужой аккаунт или URL-флаг не дают ложного успеха.
- Приглашение открывает новую вкладку; обновление user/capability при возвращении
  сохраняет ввод. Старые диалоги и доступные действия кабинета не блокируются.
  StrictMode, поздние ответы и проверки в скрытой вкладке учтены.

Границы выполненной приёмки — в [frontend README](../../frontend/README.md#результаты-проверок).
